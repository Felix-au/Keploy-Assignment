## 1. The Modern Go Testing Dilemma

Go is celebrated for its simplicity, concurrency model, and lightning-fast compiler. Yet, when it comes to microservice integration testing, Go developers frequently find themselves trapped between two suboptimal paradigms:

### Why Keploy is Fundamentally Different

Keploy flips the traditional testing pyramid on its head:

1. **Zero-Code Instrumentation**: You don't import an SDK or decorate your handlers. Your Go binary remains pristine and production-ready.
2. **eBPF-Powered Kernel Interception**: Keploy attaches probes to Linux kernel socket syscalls (`connect`, `sendto`, `recvfrom`), capturing inbound HTTP requests and outbound network calls at the protocol layer.
3. **Wire-Level Dependency Mocking**: Instead of mocking Go structs, Keploy records the raw TCP bytes sent between your application and external dependencies (MongoDB, PostgreSQL, Redis, gRPC, HTTP).
4. **Intelligent Noise Detection**: Keploy automatically recognizes dynamic fields (like timestamps, UUIDs, and JWT expirations) and eliminates false-positive test failures out of the box.

### The Architecture in Detail

When Keploy wraps your application container:

- **Ingress Hooking**: Keploy listens on the inbound port. When a test client or QA tester issues an HTTP request, Keploy logs the exact request parameters (method, URL, headers, and body).
- **Egress Virtualization**: When the Gin handler initiates a connection to MongoDB on port 27017, Keploy's eBPF driver intercepts the socket descriptor. During **Record Mode**, Keploy allows the packet to reach the real MongoDB server, simultaneously storing the binary request and response frames into `mocks.yaml`.
- **Offline Mock Serving**: During **Replay Mode**, the test runner fires the captured HTTP request into the application. When the application tries to talk to MongoDB, Keploy short-circuits the connection at the kernel level and serves the matching BSON response straight from `mocks.yaml`. The real MongoDB instance can be completely shut down!
