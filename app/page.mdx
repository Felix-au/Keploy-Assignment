## 1. The Modern Go Testing Dilemma

Go is celebrated for its simplicity, concurrency model, and lightning-fast compiler. Yet, when it comes to microservice integration testing, Go developers frequently find themselves trapped between two suboptimal paradigms:

<div className="grid grid-cols-1 md:grid-cols-2 gap-4 not-prose my-6">
  <Card title="The Unit Mocking Trap" icon="⚠️">
    Writing interfaces for every database repository, external client, and cache, followed by generating thousands of lines of boilerplate with <code>mockgen</code>. When your MongoDB schema or SQL query changes, the mocks stay green while production silently crashes.
  </Card>
  <Card title="The Ephemeral DB Fragility" icon="💥">
    Spinning up ephemeral MongoDB or PostgreSQL instances with <code>dockertest</code> or <code>docker-compose</code>. CI builds slow down by 15 minutes, state leaks between test runs, dynamic timestamps cause assertions to fail, and test databases become a maintenance nightmare.
  </Card>
</div>

### Why Keploy is Fundamentally Different

Keploy flips the traditional testing pyramid on its head:

1. **Zero-Code Instrumentation**: You don't import an SDK or decorate your handlers. Your Go binary remains pristine and production-ready.
2. **eBPF-Powered Kernel Interception**: Keploy attaches probes to Linux kernel socket syscalls (`connect`, `sendto`, `recvfrom`), capturing inbound HTTP requests and outbound network calls at the protocol layer.
3. **Wire-Level Dependency Mocking**: Instead of mocking Go structs, Keploy records the raw TCP bytes sent between your application and external dependencies (MongoDB, PostgreSQL, Redis, gRPC, HTTP).
4. **Intelligent Noise Detection**: Keploy automatically recognizes dynamic fields (like timestamps, UUIDs, and JWT expirations) and eliminates false-positive test failures out of the box.

<InteractiveDiagram />

### The Architecture in Detail

When Keploy wraps your application container:

- **Ingress Hooking**: Keploy listens on the inbound port. When a test client or QA tester issues an HTTP request, Keploy logs the exact request parameters (method, URL, headers, and body).
- **Egress Virtualization**: When the Gin handler initiates a connection to MongoDB on port 27017, Keploy's eBPF driver intercepts the socket descriptor. During **Record Mode**, Keploy allows the packet to reach the real MongoDB server, simultaneously storing the binary request and response frames into `mocks.yaml`.
- **Offline Mock Serving**: During **Replay Mode**, the test runner fires the captured HTTP request into the application. When the application tries to talk to MongoDB, Keploy short-circuits the connection at the kernel level and serves the matching BSON response straight from `mocks.yaml`. The real MongoDB instance can be completely shut down!

## 3. The Sample Application: Gin + MongoDB URL Shortener

For this tutorial, we will use Keploy's official Go quickstart: a URL shortener microservice built with **Gin** and **MongoDB 6.0**.

<CodeBlock
  lang="go"
  filename="samples-go/gin-mongo/handler.go"
  code={`package main

import (
	"context"
	"math/rand"
	"net/http"
	"time"

	"github.com/gin-gonic/gin"
	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
)

type url struct {
	Url string \`json:"url"\`
}

// urlShortner handles POST /url - generates a short key and persists to Mongo
func urlShortner(c *gin.Context) {
	var req url
	if err := c.ShouldBindJSON(&req); err != nil {
		c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
		return
	}

	shortURL := shortUrlGenerator()
	collection := client.Database("keploy").Collection("urls")

	_, err := collection.InsertOne(context.Background(), bson.M{
		"url":       req.Url,
		"short_url": shortURL,
		"ts":        time.Now(), // DYNAMIC FIELD: Keploy automatically flags this as noise!
	})
	if err != nil {
		c.JSON(http.StatusInternalServerError, gin.H{"error": err.Error()})
		return
	}

	c.JSON(http.StatusOK, gin.H{
		"status": "success",
		"url":    "http://localhost:8080/" + shortURL,
	})
}`}
/>

## 11. Real-World Field Guide & Troubleshooting

During our hands-on evaluation on Windows 11 and Docker Desktop, we encountered several non-trivial edge cases. Here are the exact solutions to save you hours of debugging:

<Accordion title="Common Gotchas & Field Solutions">
  <AccordionItem title="Docker Not Found in Keploy Container (sh: 1: docker: not found)" badge="Exit Code 127">
    <strong>The Problem:</strong> When Keploy runs inside <code>ghcr.io/keploy/keploy</code> and executes your <code>-c "docker run ..."</code> command, it looks for the <code>docker</code> binary inside its own container filesystem. If the base image lacks the Docker CLI, the command exits with code 127.
    <br /><br />
    <strong>The Fix:</strong> Extract a static Linux docker CLI binary into a local folder and mount it into <code>/usr/bin/docker</code>:
    <pre className="text-xs font-mono my-2 bg-slate-900 text-slate-100 p-2 rounded">
docker run --rm --entrypoint cat docker:cli /usr/local/bin/docker &gt; ./docker-bin/docker
chmod +x ./docker-bin/docker
# Add mount to Keploy container:
-v "$(pwd)/docker-bin:/usr/bin/docker"
